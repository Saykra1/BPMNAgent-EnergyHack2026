# Реализованные возможности

## Обязательная часть (фаза 0)

| Требование | Реализация | Где |
|---|---|---|
| Вход — текстовое описание | поле ввода; загрузка txt, docx, pdf и расшифровок интервью; длинные тексты по частям | `docimport.py`, `ir/merge.py` |
| Участники, последовательность, ветвления, параллельность | IR: участники → пулы и дорожки; XOR, AND, OR, событийные шлюзы, ветка по умолчанию, циклы, подпроцессы, события, граничные таймеры | `llm/plan.py`, `bpmn/diagram.py` |
| BPMN 2.0, валидный по XSD | детерминированный сборщик; проверка по официальным XSD OMG (`bpmn/schemas`) | `bpmn/serializer.py`, `bpmn/xsd.py` |
| Открывается в bpmn.io с DI | BPMNShape и BPMNEdge с координатами, отдельные планы для подпроцессов; импорт в bpmn-js проверяется в eval и в UI | `bpmn/layout.py`, `tools/render.mjs` |
| Модель заменяема | один адаптер `complete(messages, schema)`, 4 провайдера, выбор через `.env` | `llm/client.py` |
| LLM не пишет XML | LLM выдаёт только IR (JSON); остальное детерминированно | `pipeline.py` |
| Самоисправление ≤ 3 | сначала правила, затем LLM чинит IR, затем честный отчёт `residual` | `pipeline.py::_repair_loop` |
| Веб-интерфейс | bpmn-js Modeler (редактирование), «Создать схему», скачивание .bpmn | `frontend/` |

Приёмка: техприсоединение (5 участников, XOR и AND) даёт XSD-валидный файл, открывается в bpmn-js
без предупреждений (`tests/test_phase0.py::test_acceptance_grid_connection`, `eval --render`).

## Фаза 1

1. **Уточняющие вопросы.** Режим «С уточнениями»: если не хватает исполнителя, условия, ветки
   «иначе» или конца процесса, возвращаются вопросы, схема не строится. Режим «Без уточнений»:
   допущения выносятся на схему аннотациями «Допущение: …». Вопросы формирует линтер
   (детерминированно) и модель.
2. **Правка диалогом.** Модель меняет IR, результат пересобирается. Возвращается diff:
   добавленные, удалённые и изменённые элементы и связи. Подсветка на схеме, откат — во вкладке
   «История». Перед правкой текущая схема с холста конвертируется в IR, поэтому ручные правки не
   теряются. Шаги нумеруются для ссылок вида «после шага 3».
3. **Линтер (20 проверок):** нет начала или конца; тупик; шаг без входа; недостижимый цикл;
   выход из конечного события; XOR без условий; XOR без ветки «иначе»; шлюз с одной веткой; лишний
   шлюз; AND без слияния; deadlock (XOR-ветки сливаются через AND); несколько стартов без причины;
   шаг без исполнителя; безымянные элементы; дубли имён; поток управления между организациями.
   У каждой проблемы есть уровень, элемент и подсказка; кнопка «Исправить» — там, где это безопасно.
4. **Объяснение и регламент.** Регламент собирается детерминированно: цель, участники, порядок
   (с развилками, параллелью, возвратами), исключения, сроки, документы, допущения и вопросы.
   Форматы Markdown и DOCX. «Объяснить простым языком» делает модель; если модели нет — правила.
5. **Импорт документов:** txt, md, docx (с таблицами), pdf (текстовый слой), srt, vtt и
   расшифровки «Имя (00:01): реплика». Длинные тексты режутся на части, IR частей объединяются:
   участники — по имени, повторы шагов на стыках удаляются, части связываются последовательно.
6. **Защита данных.** До отправки в модель маскируются ФИО (полные и с инициалами), телефоны,
   e-mail, ИНН, СНИЛС, ОГРН, паспорта, карты и номера договоров; опционально — адреса и названия
   энергообъектов. После ответа значения подставляются обратно. В UI видно, что замаскировано;
   есть кнопка «Проверить ПДн». Режим `LLM_ONPREM_ONLY` пускает только локальные endpoint.
7. **Журнал действий ИИ.** Для каждого запуска: модель, версии промптов, промпт, ответ, токены,
   время, режим структурированного вывода, найденные ошибки, автоисправления, ремонты, остаток.
   Страница во вкладке «Инструменты → Журнал ИИ», экспорт JSON. API-ключи и токены вычищаются.

## Фаза 2

8. **Узкие места.** Длительность и ожидание задаются в карточке шага или в IR, оцениваются моделью
   (помечаются «оценка») или берутся типовыми по типу шага (тоже помечаются). Считаются
   критический путь и тепловая карта (работа, ожидание или сумма) с цветом и метками на схеме.
   Есть режим «как есть / как будет».
9. **Симуляция Monte Carlo** (1000 прогонов, воспроизводимый seed). Показывает среднее, p50, p90,
   гистограмму, загрузку участников и доли ветвей. Учитываются вероятности ветвей, параллельные
   ветви (по максимуму), инклюзивные слияния, циклы и срабатывание SLA-таймеров.
10. **RACI** из IR: R — исполнитель; A, C, I — из IR или выводятся (руководитель, следующий
    исполнитель, получатель сообщения) с пометкой. Экспорт CSV и XLSX.
11. **SLA и KPI.** `sla_hours` у шагов, граничные таймеры BPMN (`boundaryEvent` + `timeDuration`,
    без прерывания задачи) с веткой эскалации. Можно попросить словами: «добавь эскалацию, если не
    выполнено за 3 дня».
12. **Шаблоны энергетики:** технологическое присоединение, допуск бригады по наряду-допуску,
    аварийная заявка, плановый ремонт оборудования, закупка ТМЦ. В шаблонах есть оценки
    длительностей, вероятности и эскалации. Выбор шаблона даёт IR, который дальше правится словами.
13. **Тест-пути:** все сценарии через XOR и OR (циклы не больше одного раза, с лимитом), с
    условиями, вероятностью и временем. Экспорт CSV и Markdown; клик подсвечивает путь на схеме.
14. **Экспорт:** BPMN, SVG, PNG, JSON IR, регламент в Markdown и DOCX. Отдельный переключатель
    добавляет пометку совместимости с Camunda 8 (атрибуты Zeebe; файл остаётся XSD-валидным).

## Фаза 3 (частично)

- Отдельные модели для шагов: `LLM_REPAIR_MODEL` используется в цикле самоисправления.
- Рекомендации по оптимизации: модель опирается на результаты линтера и симуляции, вывод помечен
  «рекомендация, не факт». Без модели — эвристики по узким местам, возвратам и загрузке.
- RAG по корпоративным регламентам не реализован (см. [limitations.md](limitations.md)).
