# Реализованные возможности

## Обязательная часть (фаза 0)

| Требование | Реализация | Где |
|---|---|---|
| Вход — текстовое описание | поле ввода; загрузка txt, docx, pdf и расшифровок интервью; длинные тексты по частям | `docimport.py`, `ir/merge.py` |
| Участники, последовательность, ветвления, параллельность | IR: участники → пулы и дорожки; XOR, AND, OR, событийные шлюзы, ветка по умолчанию, циклы, подпроцессы, события, граничные таймеры | `llm/plan.py`, `bpmn/diagram.py` |
| BPMN 2.0, валидный по XSD | детерминированный сборщик; проверка по официальным XSD OMG (`bpmn/schemas`) | `bpmn/serializer.py`, `bpmn/xsd.py` |
| Открывается в bpmn.io с DI | BPMNShape и BPMNEdge с координатами, отдельные планы для подпроцессов; импорт в bpmn-js проверяется в eval и в UI | `bpmn/layout.py`, `tools/render.mjs` |
| Модель заменяема | один адаптер `complete(messages, schema)`, 4 провайдера, выбор через `.env` | `llm/client.py` |
| LLM не пишет XML | LLM выдаёт только IR (JSON); остальное детерминированно | `pipeline.py` |
| Самоисправление ≤ 3 | сначала правила, затем LLM чинит IR, затем честный отчёт `residual` | `pipeline.py::_repair_loop` |
| Веб-интерфейс | bpmn-js Modeler (редактирование), «Создать схему», скачивание .bpmn | `frontend/` |

Приёмка: техприсоединение (5 участников, XOR и AND) даёт XSD-валидный файл, открывается в bpmn-js
без предупреждений (`tests/test_phase0.py::test_acceptance_grid_connection`, `eval --render`).

## Фаза 1

1. **Уточняющие вопросы.** Режим «С уточнениями»: если не хватает исполнителя, условия, ветки
   «иначе» или конца процесса, возвращаются вопросы, схема не строится. Режим «Без уточнений»:
   допущения выносятся на схему аннотациями «Допущение: …». Вопросы формирует линтер
   (детерминированно) и модель.
2. **Правка диалогом.** Модель меняет IR, результат пересобирается. Возвращается diff:
   добавленные, удалённые и изменённые элементы и связи. Подсветка на схеме, откат — во вкладке
   «История». Перед правкой текущая схема с холста конвертируется в IR, поэтому ручные правки не
   теряются. Шаги нумеруются для ссылок вида «после шага 3».
3. **Линтер (20 проверок + проверки кода блоков):** нет начала или конца; тупик; шаг без входа; недостижимый цикл;
   выход из конечного события; XOR без условий; XOR без ветки «иначе»; шлюз с одной веткой; лишний
   шлюз; AND без слияния; deadlock (XOR-ветки сливаются через AND); несколько стартов без причины;
   шаг без исполнителя; безымянные элементы; дубли имён; поток управления между организациями.
   У каждой проблемы есть уровень, элемент и подсказка; кнопка «Исправить» — там, где это безопасно.
4. **Объяснение и регламент.** Регламент собирается детерминированно: цель, участники, порядок
   (с развилками, параллелью, возвратами), исключения, сроки, документы, допущения и вопросы.
   Форматы Markdown и DOCX. «Объяснить простым языком» делает модель; если модели нет — правила.
5. **Импорт документов:** txt, md, docx (с таблицами), pdf (текстовый слой), srt, vtt и
   расшифровки «Имя (00:01): реплика». Длинные тексты режутся на части, IR частей объединяются:
   участники — по имени, повторы шагов на стыках удаляются, части связываются последовательно.
6. **Защита данных.** Перед каждым запросом к модели `PrivacyGuard` (`backend/app/privacy.py`)
   маскирует ФИО (Natasha и правила), телефоны, e-mail, ИНН, СНИЛС, ОГРН, паспорта вместе с данными о
   выдаче, карты, счета, адреса и номера документов. После ответа значения подставляются обратно.
   Панель «Что увидит модель» под полем описания показывает обе версии текста. Режим
   `LLM_ONPREM_ONLY` пускает только локальные endpoint.
7. **Журнал действий ИИ.** Для каждого запуска: модель, версии промптов, промпт, ответ, токены,
   время, режим структурированного вывода, найденные ошибки, автоисправления, ремонты, остаток.
   Страница во вкладке «Инструменты → Журнал ИИ», экспорт JSON. API-ключи и токены вычищаются.

## Фаза 2

8. **Узкие места.** Длительность и ожидание задаются в карточке шага или в IR, оцениваются моделью
   (помечаются «оценка») или берутся типовыми по типу шага (тоже помечаются). Считаются
   критический путь и тепловая карта (работа, ожидание или сумма) с цветом и метками на схеме.
   Есть режим «как есть / как будет».
9. **Симуляция Monte Carlo** (1000 прогонов, воспроизводимый seed). Показывает среднее, p50, p90,
   гистограмму, загрузку участников и доли ветвей. Учитываются вероятности ветвей, параллельные
   ветви (по максимуму), инклюзивные слияния, циклы и срабатывание SLA-таймеров.
10. **RACI** из IR: R — исполнитель; A, C, I — из IR или выводятся (руководитель, следующий
    исполнитель, получатель сообщения) с пометкой. Экспорт CSV и XLSX.
11. **SLA и KPI.** `sla_hours` у шагов, граничные таймеры BPMN (`boundaryEvent` + `timeDuration`,
    без прерывания задачи) с веткой эскалации. Можно попросить словами: «добавь эскалацию, если не
    выполнено за 3 дня».
12. **Шаблоны энергетики:** технологическое присоединение, допуск бригады по наряду-допуску,
    аварийная заявка, плановый ремонт оборудования, закупка ТМЦ. В шаблонах есть оценки
    длительностей, вероятности и эскалации. Выбор шаблона даёт IR, который дальше правится словами.
13. **Тест-пути:** все сценарии через XOR и OR (циклы не больше одного раза, с лимитом), с
    условиями, вероятностью и временем. Экспорт CSV и Markdown; клик подсвечивает путь на схеме.
14. **Экспорт:** BPMN, SVG, PNG, JSON IR, регламент в Markdown и DOCX. Отдельный переключатель
    добавляет пометку совместимости с Camunda 8 (атрибуты Zeebe; файл остаётся XSD-валидным).

## Свойства блока, исполнители и роли

- **Шестерёнка ⚙** появляется у выделенного блока, связи или дорожки. Она открывает окно со всеми
  свойствами блока:
  - название и тип (задача: пользовательская, сервисная, ручная и др.; шлюз: XOR, AND, OR, по событию);
  - описание своими словами;
  - роль (дорожка), в том числе новая роль прямо из окна;
  - исполнитель из справочника или новый;
  - срок и точка отсчёта, норматив SLA, работа и ожидание (с пометкой «оценка»);
  - документы, цитата-основание и допущение;
  - RACI (A, C, I);
  - для развилки — условия веток, ветка «иначе» и вероятности.
- **Удаление блока, связи или пустой роли** — из того же окна.
- **Отмена и история.** Все изменения идут через стек команд bpmn-js: работают Ctrl+Z, история
  версий и проверки.
- **«Ещё → Исполнители и роли».** Справочник исполнителей: ФИО, должность, роль, контакты. Здесь же
  можно переименовать и добавить роли (дорожки).
- **Хранение в .bpmn.** Справочник хранится на процессе (`BPMN_AGENT_PERFORMERS`), описание — в
  обычном `bpmn:documentation`, остальные поля — в `BPMN_AGENT_DETAILS`. Файл остаётся XSD-валидным,
  при обратной конвертации в IR ничего не теряется (`performers`, `description`, `performer`,
  вероятности веток).
- **Использование данных.** Исполнитель и описание попадают в регламент (таблица исполнителей,
  «Роль (ФИО, должность)» в шагах) и в RACI.
- **Защита справочника.** При правке словами, самоисправлении, объяснении и рекомендациях модель
  получает справочник обезличенным («Исполнитель 1»). Реальные данные подставляются обратно по id.

## Код блоков, проверки развилок и документы о работе

- **Код автоматического шага.** У сервисной задачи (а также скрипта, бизнес-правила и отправки) в
  свойствах (⚙) есть поле «Код шага» — несколько строк на подмножестве Python над данными процесса.
  - Пример: `сумма = sum([p["цена"] * p["кол"] for p in позиции])`.
  - Доступны if/for/while, f-строки, списки и словари, функции `len`, `sum`, `round`, `today()`,
    `add_workdays(дата, n)`, `days_between`, `value("имя", по_умолчанию)`, `log(...)` и `fail("причина")`.
  - Кнопка «Проверить код» прогоняет код на тестовых данных и показывает, какие данные изменились,
    журнал и готовый документ.
- **Проверки развилок.** У каждой ветки XOR/OR-шлюза есть поле «Проверка» — выражение, например
  `сумма > лимит and решение == "да"`.
  - XOR идёт по первой ветке с истинной проверкой, иначе по ветке «иначе». OR идёт по всем истинным.
  - Если проверок нет, ветку выбирают вручную при запуске.
  - Кнопка «Проверить проверки» показывает, какая ветка сработает на тестовых данных.
- **Документ о выполненной работе.**
  - Автоматический шаг формирует DOCX сам: шаблон с подстановкой `{переменных}`, изменённые данные
    и журнал `log()`.
  - Шаг человека (задача, пользовательская, ручная, получение) задаёт список данных, которые
    вводит исполнитель, и подсказку, что должно быть в документе.
- **Запуск процесса** («Ещё → Выполнить процесс»):
  - процесс выполняется по текущей схеме с исходными данными (JSON);
  - автоматические шаги исполняют код;
  - на шаге человека запуск ждёт: исполнитель вводит данные и обязательно формирует документ
    (текст → DOCX) или прикрепляет файл (до 10 МБ);
  - поддерживаются параллельные ветки со слиянием, инклюзивные развилки, подпроцессы и
    терминирующее завершение;
  - на схеме видно пройденные шаги, ожидающие и шаг с ошибкой;
  - при ошибке в коде запуск останавливается с номером строки; после исправления схемы кнопка
    «Повторить шаг» продолжает с того же места;
  - можно скачать каждый документ, приложения и архив ZIP (документы, приложения, журнал,
    итоговые данные, BPMN). Состояние запуска хранится на сервере (`runs/_instances`) и
    переживает перезагрузку страницы.
- **Хранение в .bpmn.** Код, шаблон и поля шага лежат в `BPMN_AGENT_DETAILS` элемента, проверка ветки —
  в `BPMN_AGENT_DETAILS` связи. Файл остаётся XSD-валидным, при обратной конвертации в IR ничего не
  теряется.
- **Безопасность кода.**
  - Код никогда не передаётся в `exec`/`eval`: собственный интерпретатор обходит AST
    (`backend/app/run/script.py`).
  - Запрещены import, def, lambda, try, доступ к атрибутам (кроме разрешённых методов строк,
    списков и словарей) и dunder-имена.
  - Лимиты: 20 000 шагов вычисления (бесконечный цикл останавливается), размер строк и списков,
    величина чисел.
  - Закрыты известные обходы: `str.format`, `%`-форматирование, огромная ширина в f-строке.
- **Код не уходит в модель.** При правке словами модель не получает код, шаблоны и проверки;
  после ответа они возвращаются по id, поэтому правка схемы их не теряет.
- **Линтер** предупреждает об ошибке синтаксиса в коде или проверке, о коде у шага человека и о
  развилке с проверками без ветки «иначе».

## Аккаунты, команды и роли

Основа — прототип команд из ветки `Asya_feature_MakeTeam`: команды, ссылки-приглашения, общие проекты
с версиями и защитой от одновременной записи. Он влит в эту ветку (`git merge`) и доработан.

- **Регистрация и вход.**
  - При регистрации указываются логин, почта, имя и пароль.
  - Пароль хранится только как хэш scrypt с солью (`collab/security.py`). Токены сеансов в базе
    тоже только в виде SHA-256.
  - Войти можно по логину, почте или личному ID.
  - После 5 неудачных попыток вход приостанавливается на 5 минут.
  - Смена пароля закрывает остальные сеансы.
  - Хранилище — SQLite `data/app.db`.
  - При `REQUIRE_LOGIN=true` (по умолчанию) весь API закрыт без входа, интерфейс показывает экран
    входа и регистрации.
- **Личный ID** — 8 символов без похожих букв, например `#7KQ2-M9XA`, виден в меню аккаунта.
- **Команды.** Любой может создать команду, дать ей название и стать её главой. Глава может всё,
  переименовывает и удаляет команду.
- **Приглашения.**
  - Приглашать можно по почте, логину или ID и сразу указать роли.
  - Приглашённый видит приглашение (счётчик на кнопке «Команды»), принимает или отклоняет его.
  - Приглашение на незарегистрированную почту появится после регистрации с этой почтой.
  - Есть ссылки-приглашения: человек входит по ссылке, видит команду и роли и сам решает, вступать
    ли.
  - Приглашения и ссылки можно отозвать.
- **Роли настраиваются полностью.** Глава (или участник с правом «Настройка ролей») создаёт,
  переименовывает, перекрашивает и удаляет роли. У каждой роли включаются права:

  | Право | Что даёт |
  |---|---|
  | Видеть проекты | открывать схемы, регламенты, документы |
  | Названия, описания, документы | названия, описания, сроки, документы, исполнители, подписи веток, текст процесса |
  | Редактировать схему | блоки, связи, дорожки, тип блока, перемещение |
  | Генерация с помощью ИИ | построение из текста и правка словами |
  | Код блоков и проверки | код автоматических шагов, проверки веток |
  | Запуск процесса | запуск и выполнение шагов |
  | Удалять проекты | — |
  | Создавать проекты | — |
  | Участники и приглашения | приглашать, исключать, выдавать роли |
  | Настройка ролей | создавать и менять роли |

  У роли также задаётся **область видимости**: все проекты команды или только выбранные.
- **Готовые роли** новой команды можно менять или удалить:
  - «Разработчик» — редактирует BPMN, генерирует с помощью ИИ, пишет код, запускает процесс и
    создаёт проекты;
  - «Администратор» — меняет только названия, описания и документы;
  - «Наблюдатель» — только просмотр.
- **Без ролей не видно ничего**: ни проектов, ни участников, ни ролей. Права участника — объединение
  прав его ролей; права в проекте дают только роли, в область видимости которых проект входит.
- **Защита от повышения прав.** Права «Участники и приглашения» и «Настройка ролей» выдаёт,
  меняет и снимает только глава.
- **Сервер проверяет каждое сохранение проекта.** Старая и новая схема переводятся в IR и
  сравниваются по частям: структура, содержимое, код, текст, раскладка. Если роли не дают права на
  изменённую часть, сохранение отклоняется с объяснением. Даже обойдя интерфейс, администратор не
  может удалить связь или блок.
- **ИИ и запуск в проекте.** Запросы к LLM внутри проекта (заголовок `X-Project-Id`) требуют права
  «Генерация с помощью ИИ», действия запуска процесса — права «Запуск процесса».
- **Интерфейс следует ролям.** Без права «Редактировать схему» скрыты палитра и контекстное меню,
  структурные команды bpmn-js не выполняются. В окне свойств блока недоступны поля, на которые нет
  прав. Кнопки генерации и запуска выключены.
- **Общие проекты.** Проект создаётся пустым или из текущей схемы. Есть версии, «Сохранить»,
  «Обновить», «Закрыть проект» и предупреждение о несохранённых изменениях. При одновременной
  записи сохраняется первая версия, вторая получает отказ «загрузите новую версию».

## Фаза 3 (частично)

- Отдельные модели для шагов: `LLM_REPAIR_MODEL` используется в цикле самоисправления.
- Рекомендации по оптимизации: модель опирается на результаты линтера и симуляции, вывод помечен
  «рекомендация, не факт». Без модели — эвристики по узким местам, возвратам и загрузке.
- RAG по корпоративным регламентам не реализован (см. [limitations.md](limitations.md)).

## Наследие прототипа (ветки stepa_1 и ранее)

Связь фраз текста и шагов схемы, аудит покрытия требований, проверка Jev, показ процесса с
маскотом, проигрывание токенов bpmn-js, поиск шагов, карточки сроков и документов, история
версий, режим генерации Python-кода на DIAGRAM API с песочницей (AST-фильтр).
