# Архитектура

## Актуальный пайплайн (IR → детерминированный сборщик)

```
text ──► check_text ──► pii.mask ──► split_text ──► LLM extract_ir (JSON Schema, few-shot, ремонт JSON ≤2)
     ──► merge_plans (если частей > 1) ──► pii.unmask ──► ground quotes
     ──► lint + questions ──(ask & есть блокирующие)──► вопросы аналитику
     ──► compile_plan (IR → DIAGRAM code, id сохраняются) ──► sandbox ──► normalize ──► validate
     ──► layout (DI) ──► serializer ──► XSD
     ──► проблемы? → autofix (правила) → LLM repair IR (≤ MAX_REPAIRS) → residual (честный отчёт)
```

- **IR** (`llm/plan.py`): участники (внутренние → дорожки, external → пулы), элементы 19 типов
  (включая `boundary_timer`), потоки с условием, `default`, `probability`, атрибуты аналитики
  (длительность, ожидание, SLA, RACI), допущения и вопросы. JSON Schema строится из pydantic и
  передаётся в LLM.
- **id элементов IR = id в BPMN**: участники становятся id дорожек и пулов, `start`/`end` — id общих
  событий. За счёт этого после правок работают diff и подсветка, а также точная обратная
  конвертация BPMN → IR (`ir/from_diagram.py`), которую проверяет тест кругового преобразования.
- **Самоисправление** (`pipeline._repair_loop`): сборка → список проблем с id IR (линтер, валидатор,
  XSD) → безопасные автоисправления → если не помогло, LLM получает свой IR и ошибки и возвращает IR
  целиком → новая сборка. После `MAX_REPAIRS` раундов строится черновик, а проблемы возвращаются в
  `residual`.
- **Правка диалогом** (`pipeline.refine`): XML с холста → IR → LLM (`ir_edit`, нумерованные шаги) →
  новый IR → тот же цикл проверок → `diff_plans` (добавлено, удалено, изменено; что подсветить).
- **Аналитика без модели**: `ir/engine.py` — движок токенов (XOR/OR-выбор, AND-join, OR-join по
  числу активированных ветвей, SLA-таймеры). На нём работают Monte Carlo (`simulate`) и
  перечисление тест-путей (`enumerate_paths`, выбор на развилках через `NeedChoice`).

# Архитектура и принятые решения (прототип)

## Конвейер

1. **Планировщик (LLM)**: текст → JSON-план (участники, элементы, связи, сообщения, группы,
   допущения, вопросы). План проверяется сразу: pydantic-схема, уникальность id, ссылки на
   участников, подпроцессы и группы. При ошибке модель получает список проблем и исправляет план
   (до 2 раундов). Сам план — понятный аналитику промежуточный артефакт: его видно во вкладке «План».
2. **Генератор кода (LLM)**: план → Python-код на DIAGRAM API (`docs/api.md`). Есть режим `direct`
   (сразу текст → код) для сравнения на eval.
3. **Песочница**: AST-whitelist. Разрешены только присваивания и вызовы `DIAGRAM.<метод из
   API>` с литералами, переменными и индексами. Запрещены импорты, атрибуты, циклы, функции,
   f-строки и dunder-имена. Builtins пустые, есть бюджет операторов и таймаут. Программа получается
   линейной и не может обратиться ни к чему, кроме API. Ошибка возвращается с номером строки.
4. **Нормализация** (безопасные автоисправления, которые попадают в отчёт): дубли связей;
   связь между пулами → поток сообщений; неиспользуемые стандартные старт и конец; неявные старт и
   конец в подпроцессах и вторичных пулах; привязка событий без дорожки к дорожке соседа;
   удаление пустых дорожек и групп.
5. **Семантический валидатор**: старт и конец есть в каждом контейнере; нет обрывов и недостижимых
   узлов; связи не пересекают границы подпроцессов; у событийного шлюза правильные цели. Ищутся
   deadlock (параллельное слияние ветвей исключающего шлюза), множественное срабатывание
   (исключающее слияние параллельных ветвей), лишние и смешанные шлюзы, неподписанные ветви.
   Ошибки уходят в repair-loop, предупреждения показываются аналитику.
6. **Раскладка** (`layout.py`): см. ниже.
7. **Сериализация**: BPMN 2.0 XML (collaboration/participant/laneSet/flowNodeRef/messageFlow/
   conditionExpression/category+group/textAnnotation+association) и BPMN DI с явными подписями.
8. **Проверки файла**: XSD OMG (`BPMNDI`, `DC`, `DI`, `Semantic`) через lxml на бэкенде; импорт в
   bpmn-js (то же, что делает bpmn.io/moddle) в браузере и в eval (`tools/render.mjs`).
9. **Repair-loop ≤ 3**: ошибки песочницы, валидатора или XSD возвращаются модели в том же диалоге
   вместе с её кодом. Если раунды закончились: **компилятор план → код** (детерминированный), затем
   мягкий режим (`lenient`: обрывы подключаются к старту и концу).

## Раскладка

Для BPMN нужны дорожки и пулы как жёсткие ограничения, выход из шлюзов вверх и вниз, обход циклов
и вертикальные потоки сообщений. Поэтому вместо универсального ELK используется своя слоевая
раскладка (по Сугияме):

1. разрыв циклов: DFS от стартовых событий, обратные рёбра — это циклы доработки;
2. слои по длиннейшему пути в DAG (потоки управления + сообщения, чтобы обмен между пулами шёл
   примерно по вертикали); источники подтягиваются к своим преемникам;
3. фиктивные узлы для рёбер через несколько слоёв: обход ветвью не проходит через задачи;
4. строки внутри дорожки: ветви разветвления занимают соседние строки, слияние возвращается на
   верхнюю входящую строку, основной путь остаётся прямой линией;
5. координаты: ширина колонки по самому широкому элементу, высота дорожки по числу строк и циклов;
6. трассировка: ортогональные ломаные. Вертикальные участки идут в промежутках между колонками,
   выход из шлюза через верх или низ — только если колонка свободна. Циклы идут через коридор у
   нижней границы дорожки, сообщения огибают узлы. Подписи условий ставятся у точки расхождения
   ветвей, подписи шлюзов — сверху, если низ занят связью.

Результат детерминирован: одинаковый код всегда даёт одинаковую схему.

## Что изменено относительно исходной схемы

| Было | Стало | Почему |
|---|---|---|
| Ошибка JSON-плана обнаруживается генератором кода | План проверяется сразу после планировщика (схема и ссылки), и планировщик исправляет его сам | ошибка ловится раньше и дешевле, генератор получает заведомо корректный план |
| Layout (ELK) + постобработка | своя раскладка с дорожками в Python | ELK — JS-зависимость на бэкенде; дорожки, выходы шлюзов, циклы и сообщения всё равно требуют своей постобработки |
| repair-loop ≤3 — последний рубеж | + детерминированный компилятор план → код + мягкий режим | аналитик всегда получает открываемую схему, а метрики честно показывают, откуда взят результат |
| XSD + moddle на выходе | XSD на бэкенде; moddle/bpmn-js — в браузере при каждом импорте и в eval | не нужен Node в рантайме бэкенда, а проверка идёт ровно тем движком, что и в bpmn.io |
| Просмотр и правка → только экспорт | + импорт XML → код | ручные правки на холсте сохраняются при диалоговых изменениях; можно доработать любой существующий `.bpmn` |
| — | Допущения и вопросы к заказчику в плане | бизнес-ценность: ассистент показывает, что домыслил и что стоит уточнить |
| — | Свёрнутые подпроцессы с отдельной диаграммой | большие процессы остаются читаемыми, внутрь можно провалиться в bpmn.io |
